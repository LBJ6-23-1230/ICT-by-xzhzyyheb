## 0. 三条分工原则（先立规矩，再分活）

1. **按"可独立交付的产物"切，不按"技术喜好"切。** 每个人手上都要有能单独验收的东西（一个服务、一个页面、一份报告），而不是"我负责智能体那一块"这种说不清边界的说法。
2. **同一个人对同一类文件有唯一写权。** 三个人同时改 `contracts/openapi.json` 或同一个 `.ets` 文件，是这类项目最常见的时间黑洞。
3. **关键路径优先。** 谁被外部依赖卡住（公测审核、域名备案），谁就先去干不依赖云的那部分活，不要干等。

**三个反模式，别这么分：**

- ❌ 按页面分（"你做聊天页、我做练习页"）——接口契约会打架，联调时互相等。
- ❌ 按"前后端"简单二分——MCP 和网关同属服务端，拆给两个人会重复实现鉴权与数据访问。
- ❌ 三个人都"参与"平台配置——控制台上的智能体/工作流只能有一个负责人，否则版本会互相覆盖。

## 2. 三个人怎么分

| | **A（队长·平台与材料）** | **B（服务端·网关与工具）** | **C（客户端·契约与呈现）** |
|---|---|---|---|
| **主责** | WP0、WP1、WP5、WP9 | WP2、WP3、WP4、WP7 | WP6、WP8 部分、WP9 视觉 |
| 人日 | ≈ 1+4+2+2 = **9** | ≈ 3+4+1+2 = **10** | ≈ 4+1+2 = **7** |
| 一句话 | 把作品"抬上云"，并负责对外讲清楚 | 把能力"接进云"，保证数据和权限不出事 | 把结果"看得见"，保证演示不出洋相 |

**A 的具体活**

1. 第 1 天：提交公测申请、确认报名状态、定域名方案（A/B/C 三选一）。
2. 建 ECS + TLS + 域名解析；开 OBS；完成 FunctionGraph / MaaS 授权。
3. 知识库：把 `md/txt` 语料转成 docx/pdf（平台不支持 md/txt）、脱敏、建库、跑命中率测试。
4. 画布：4 条能力工作流 + 意图识别工作流 + 控制器；写角色提示词；配等待输入/跳转上限。
5. 发布版本、记 `agent_id/version`；每周归档一次调用链。
6. Web Demo 页面（与 C 共用一套视觉规范）。
7. 作品说明、6 张图、资产清单、答辩稿、社区分享帖。

**B 的具体活**

1. 网关：`agentarts/{config,auth,client,events,session}.py`、`api/agentarts_api.py`、SSE 解析与事件映射。
2. 会话：`conversation_id` 生成、`sessionRef` 签发与换绑、`agentarts_sessions` 集合。
3. MCP：11 个工具封装（**只准调用现有函数，不准重写业务规则**）、统一信封、API Key、幂等、越权拦截。
4. 部署：Dockerfile + compose + Nginx/Caddy TLS + `/healthz`；写部署与回滚文档。
5. 契约：`openapi.json` v0.4 + fixtures + `diff_contracts.py`；**契约变更的唯一出口**。
6. 评测：30 条评测集 + 本地断言脚本 + 平台评测执行 + 报告。

**C 的具体活**

1. App 8 个文件：`ApiDefaults`、`AgentApiClient`、`AgentBridge`、`ChatModels`、`ApiResponseValidator`、`ApiDisplayFormatter`、`ChatMain`、`AgentTrace`。
2. 事件轮询（`GET /api/v2/agent/runs/{id}?after=N`）与断线重连；云端/降级徽标。
3. 三个测试文件同步；保证 `ExerciseFlow.test.ets` 里写死的 `baseUrl` 与 mastery 42→58 断言不失效。
4. "去假"清理：默认关闭离线体验入口、隔离"模拟 AI 识别"路径。
5. 演示资产：截图、录屏、3 分钟视频剪辑、材料排版。
6. 端到端验证：主场景 + 三类故障在 App 上实际点一遍。

**明确"不碰"清单（防止互相踩）**

| 人 | 可以写 | 只读 / 不碰 |
|---|---|---|
| A | `06-华为ICT大赛改造/**`、`web/**`、`evidence/trace/**`、云控制台 | `server/**`、`app/**`、`contracts/**` |
| B | `server/**`、`mcp/**`、`contracts/**`、`tools/**`、`docker-compose.yml` | `app/**`、`web/**`、`06-…/**` |
| C | `app/**`、`演示测试数据/**`、`evidence/demo-*`（截图视频） | `server/**`、`contracts/**`、`mcp/**` |

> 需要改别人的文件时：提一句、由owner改，或者开分支后请owner合并。**不要"顺手改一下"。**

**如果能力不匹配可以对调，但守住两条**：

- WP2 + WP3 必须同一个人（共享鉴权、会话、Repository）。
- WP5 + WP6 可以拆给两个人（一个做 Web、一个做 App），但契约由 B 统一出口。

## 3. 四个硬交接点（错过就是返工）

| # | 交接内容 | 交出方 → 接收方 | 时间点（相对） | 判定标准 |
|---|---|---|---|---|
| H1 | 事件模型与 v2 端点定稿 | B → C、A | 第 1 周末 | 字段表冻结，写进 `contracts/openapi.json`，`diff_contracts.py` 过 |
| H2 | MCP 公网可发现 | B → A | 第 2 周前半 | 平台"创建 MCP"能自动发现 11 个工具 |
| H3 | 控制器发布版可调用 | A → B、C | 第 3 周前半 | `curl` 能拿到流式返回且 `plugin_*` 事件有工具名 |
| H4 | 演示脚本冻结 | 全体 → C（录制） | 第 4 周前半 | 主场景 + 一次失败恢复，连跑 3 次不掉链子 |

> **倒排方式**：拿到官方"材料提交截止"后，设它为 T，则第 4 周 = T 前 1 周、第 1 周 = T 前 4 周。若前置资源（公测审核、备案）比预期多耗 5 个工作日以上，不延期，而是砍范围：先砍 WP6（App 改造），保 Web Demo + MCP + 控制器。

## 4. 协作规则

**版本与分支**

- `main` 只放可运行版本；每人一条长期分支 `feat/a-platform`、`feat/b-server`、`feat/c-client`。
- 合并窗口：每天 21:00 前合一次；周五做一次完整回归（`pytest` + `diff_contracts.py` + App 构建）。
- 禁止直接 push `main`；合并前至少一人看过 diff。

**契约变更流程（唯一）**

1. 需求提出 → B 判断是否改契约。
2. B 改 `contracts/openapi.json` + `app/contracts/` 镜像 + fixtures，跑 `python tools/diff_contracts.py`。
3. B 在群里发"契约变更 v0.4.1：新增 X 字段"。
4. C 才动 DTO 与页面。**顺序反了就是白改。**

**每日同步（15 分钟，固定问三句）**

1. 昨天交付了什么（对应哪个 WP）？
2. 今天卡在哪（是技术问题还是等外部）？
3. 有没有动到别人的文件？

**周节奏建议**

| 周内节奏 | A | B | C |
|---|---|---|---|
| 周一 | 平台/资源推进 | 网关开发 | App 契约层 |
| 周二~周三 | 知识库与工作流 | MCP 工具 + 部署 | 页面渲染 |
| 周四 | 控制器与发布 | 越权/幂等测试 | Web 视觉对齐 + 测试 |
| 周五 | Trace 归档 + 材料 | 契约冻结 + 回归 | 打包构建 + 截图 |
| 周末 | 各自补进度，不排会议 | | |

## 6. 开工第一天就该做的三件事

1. **A**：提交 AgentArts 公测申请（审核约 5 个工作日，通过后才能开始建资产）；同时确认报名是否已提交成功。
2. **A + B**：定 MCP 域名方案——有备案域名 / 香港节点 / 大陆新备案，三选一，第一天定，别拖。
3. **B**：先用本地假 SSE 服务把网关解析器和事件映射写出来，不等公测。

> 判断标准很简单：**到第 1 周末，H1 没交接出去，就说明分工没落地**，要立刻收缩范围（先砍 WP6 App 改造，保 Web Demo + MCP + 控制器）。
