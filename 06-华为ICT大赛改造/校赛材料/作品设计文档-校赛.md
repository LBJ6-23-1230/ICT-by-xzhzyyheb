## 一、作品概述

**一句话**：把「学生今天该学什么」这件事，从"凭感觉"变成"有依据、可核验、会随做题结果自动调整"。

学生真正的困难不是没有题做，而是：

1. 错题越攒越多，但不知道下一步该补哪一块；
2. 计划表排得很漂亮，一遇到作业和考试截止就崩；
3. 问 AI"我哪里薄弱"，得到的往往是通用建议，**没有一条能追到自己的数据**。

知学 Mate 用 **AgentArts 多智能体**把这些串成一个闭环：

```text
上传讲义 → 按资料出题 → 作答 → 确定性判分 → 掌握度变化
                                   ↓
                       错题自动入库 → 诊断更新 → 计划重排
```

**创意点**：界面上的每个数字都能点开看依据——分数追到判分规则，引用追到讲义章节与片段哈希。
模型负责解释，**不允许它报数字**。

## 二、场景定义与真实问题

| 维度 | 说明 |
|---|---|
| 目标用户 | 大学生（有明确课程、有作业与考试截止日期） |
| 使用场景 | 晚自习前 30 分钟决定"先做什么"；错题复盘；考前两周冲刺 |
| 现有方案的问题 | 题库类产品只管刷题，不管"该不该刷这道"；计划类产品不会随成绩变化调整 |
| 我们的切入 | 用"课程 → 知识点 → 掌握度"这条数据链，把出题、判分、诊断、排期绑在一起 |

**冷启动口径（重要）**：新用户第一次进入时**没有任何学习数据**。
系统请他填写课程与知识点，这些条目以「未评估」状态加入学情——此时诊断会明确说"还没测过，建议先做 3 题短测"，
**不会把"未评估"误报成"薄弱"**。第一次判分之后，才有真实的掌握度。

## 三、Agent 设计方案（AgentArts 平台）

### 3.1 总体架构

```text
┌──────────────────────────── Web Demo（单页，浏览器）────────────────────────────┐
│ 对话 / 执行时间线 / 运行详情 / 上传讲义 / 拍错题 / 课程表 / DDL / 错题本        │
└───────────────────────────────────┬────────────────────────────────────────────┘
                                    │ SSE
┌───────────────────────────────────▼────────────────────────────────────────────┐
│ Flask 网关                                                                      │
│  · 会话与身份（sessionRef）      · 平台事件归一化（7 类 → 内部事件）             │
│  · 判分聚合（工具 → 掌握度 → 重排 → 平台点评）                                  │
│  · 降级分层（平台不可用时，数字与解析仍可用，并显式标注）                        │
└───────────────┬─────────────────────────────────────┬──────────────────────────┘
                │ Bearer（运行时）                     │ X-API-Key（直连 MCP）
┌───────────────▼──────────────────┐   ┌──────────────▼───────────────────────────┐
│ AgentArts 多智能体控制器          │   │ MCP 服务（12 个工具，HTTPS + API Key）    │
│  ├ wf-diagnosis  学情诊断/讲题    │   │  · 读：上下文/检索/证据/优先级/预算/判分  │
│  ├ wf-planner    学习规划         │   │  · 写：存计划/更新掌握度/请求重排/记错题  │
│  ├ wf-exercise   按资料出题       │   │  · 数据：SQLite（画像/计划/题库/资料/     │
│  ├ wf-assessment 评估与点评       │   │          错题/课程/DDL/知识点注册表）     │
│  └ wf-chat       兜底应答（建议） │   └───────────────────────────────────────────┘
└──────────────────────────────────┘
```

**为什么这样切分**：

| 层 | 负责 | 不负责 |
|---|---|---|
| AgentArts | 理解意图、分派、组织语言、解释结果 | 计算分数、预算、掌握度 |
| 网关 | 会话、事件翻译、聚合调用、降级 | 业务判断 |
| MCP 工具 | 所有确定性计算与数据读写 | 生成式表达 |

> 这条边界是本作品的核心工程主张：**模型只判断，不算数。**

### 3.2 智能体清单与职责

| 智能体 | 触发意图 | 输入 | 输出 | 提示词要点 |
|---|---|---|---|---|
| **控制器**（多智能体） | 所有输入 | `query`、`sessionRef`、`resultText`(可选) | 分派或直接应答 | 判断顺序 1–6，命中即停；禁止静默结束；转交时透传参数；
不改写子工作流返回的数字 |
| `wf-diagnosis` | 哪里薄弱 / 为什么错 / 这题错在哪 | `query`、`sessionRef` | 薄弱点排序，或题目讲解 | 先判断是不是"具体题目"：是则先讲题再定位知识点；`assessed=false` 的不能说薄弱 |
| `wf-planner` | 怎么安排 / 时间不够 / 先排计划 | `query`、`sessionRef`、`availableMinutes` | 候选计划 JSON → 预算裁剪 → 中文计划 | 只产候选计划，**不自己删任务**；超预算交给 `fit_plan_to_budget`；优先处理 ≤3 天截止 |
| `wf-exercise` | 出几道题 / 想练练 / 根据资料出题 | `query`、`sessionRef` | 一句引导语（题目由界面渲染成答题卡） | 不复述题干选项；失败如实说明，不编题 |
| `wf-assessment` | 交卷 / 我做得怎么样 / 要不要改计划 | `query`、`sessionRef`、`resultText` | 2 句点评 | **不重新判分**（判分已由工具完成）；只用给定数字 |
| `wf-chat`（建议新增） | 闲聊 / 身份 / 缺信息 | `query`、`sessionRef` | 1–3 句 | 兜底，避免控制器"无人可派"时静默结束 |

### 3.3 工作流架构（节点级）

**wf-diagnosis**

```text
开始(query, sessionRef) → 工具 get_learning_evidence → 大模型（讲题/薄弱点）→ 结束
```

**wf-planner**

```text
开始 → 工具 get_learning_context → 大模型A（出候选计划 JSON）
     → 工具 fit_plan_to_budget（预算裁剪）
     → 大模型B（写中文计划：保留/延期/原因）
     → 结束
```

**wf-exercise**

```text
开始(query, sessionRef) → 工具 create_grounded_exercise
     → 大模型（一句引导语）→ 结束
```

**wf-assessment**

```text
开始(query, sessionRef, resultText) → 大模型（点评）→ 结束
```

> 设计说明：早期版本在 `wf-assessment` 里放了 `grade_exercise / update_mastery / request_replan` 三个工具节点，
> 结果与网关的判分链路**重复扣分**（同一道错题掌握度掉两次）。现已改为"只点评、不判分"。

### 3.4 工具编排（MCP，12 个）

| 工具 | 读/写 | 关键约束 |
|---|---|---|
| `get_learning_context` | 读 | 一次返回画像、计划、薄弱点、**课程与 DDL**（避免新增工具导致平台 schema 刷新） |
| `search_learning_materials` | 读 | 返回文件名 / 章节 / 片段哈希，供"引用可点开" |
| `get_learning_evidence` | 读 | 含 `assessed`、错题数、证据条数 |
| `calculate_learning_priority` | 读 | 五因子排序（掌握度/错误强度/重要度/紧迫度/时间） |
| `fit_plan_to_budget` | 读 | 整任务排入，排不下的进 `unscheduledTasks` 并给原因；不拆分任务 |
| `grade_exercise` | 读 | **只认服务端答案键**；返回逐题对错 + 正确答案 + 解析 + 来源 |
| `get_plan_diff` | 读 | 版本间任务差异 |
| `create_grounded_exercise` | 读 | 只按资料出题；无依据返回 `INSUFFICIENT_MATERIALS`；引文由服务端截取 |
| `save_learning_plan` | 写 | 乐观锁 `expectedVersion` + 幂等键 |
| `update_mastery` | 写 | 按固定规则换算（满分 +29、<60 −4 …），全部经知识点注册表归一 |
| `request_replan` | 写 | 显式返回 `needReplan / reasons / planDiff` |
| `record_wrong_question` | 写 | 记错题 + 下调掌握度（用户确认做错时使用） |

**调用约定**：写操作必须带幂等键；身份只能由 `sessionRef` 换取，**不接受模型传 `userId`**。

### 3.5 知识接入（从讲义到可核验引用）

```text
用户上传讲义（PDF / DOCX / MD / TXT）
  → 解析切片（章节路径 + 正文）
  → 知识点抽取：内置词表 + 标题规则（确定性，不依赖模型）
  → 用户可在"课程与知识点"里确认/改名/归入课程
  → 出题与检索按知识点匹配，返回：文件名 + 章节 + 片段哈希
```

**引用可核验**：片段哈希由切片文本计算，界面点开即可对照原文——
"依据"不是模型写的一句话，而是一条能验证的链接。

### 3.6 模型与资产选择

| 资产 | 选择 | 理由 |
|---|---|---|
| 控制器模型 | DeepSeek-V4.1-Flash（平台） | 分派与组织语言，成本低 |
| 工作流模型 | 同上 | 统一口径，便于追溯 |
| 出题模型 | 服务器侧 OpenAI 兼容端点（可切华为云 MaaS） | 出题是批量 JSON 生成，独立配置便于换供应商 |
| 会话 | `x-hw-agentarts-session-id`（运行时会话） | 平台原生，1–32 位、7 天有效 |
| 观测 | 运行时日志 / 指标 / 调用链（均开启） | 答辩时用 Trace 证明"真的在调工具" |
| 部署 | 智能体运行时（API Key 入站认证） | 初始化快（秒级），不需要绑定公网 IP |

### 3.7 部署与降级

```text
启动时间：秒级（运行时）
入站认证：API Key（与网关 .env 一致）
降级口径：
  平台不可用 → 分数/解析/错题本仍可用（本机工具），评语显示"本次不可用：<code>"
  完全无法分派 → 网关给一句能力引导，事件标注 fallback=local（不冒充模型回答）
```

## 四、创新点

### 创新点 1：可核验的依据链（交互方式创新）

界面上每个数字、每条建议都能点开：

```text
掌握度 42  [🧮 计算]  → 规则 R1–R5 + 错题记录 + 画像版本
建议"先练二叉树"  [📚 资料] → 文件名 + 章节 + 片段哈希 + 原文
```

市面上学习产品都在"给建议"，很少有产品把**建议的依据**摆出来。这也是我们敢让评委现场抽查的原因。

### 创新点 2：模型不算数（架构创新）

判分、预算裁剪、掌握度换算、是否重排 —— 全部是确定性代码。
模型只做两件事：分派、解释。由此得到两个可验证的结果：

- 同一份作答，任何人跑都得到同一个分数；
- 平台模型不可用时，分数与解析仍然正确（只是少一句评语）。

### 创新点 3：未评估 ≠ 薄弱（数据伦理）

用户自填的知识点状态是"未评估"，诊断不会把它当成 0 分的薄弱点，而是提示先做短测。
这条看似小，但它决定了系统**不会用编造的数据吓唬用户**。

## 五、应用价值

| 维度 | 说明 |
|---|---|
| 真实需求 | 大学生普遍存在"知道要学但不知道先学什么"的决策成本 |
| 可复制 | 工具与学科无关；换一门课只需换讲义与知识点清单（已在数据结构 / 计算机网络 / 概率论三类验证字段） |
| 可规模化 | 单用户数据量小（画像 + 计划 + 错题），单机 SQLite 可支撑演示与百人级试用；横向扩展只需换 PostgreSQL |
| 成本 | 一次问答调用 1 个模型 + 1–2 个工具；出题是唯一较慢环节（约 30–60 秒），可提前生成 |
| 落地路径 | 已具备：多智能体编排、MCP 工具化、知识接入、部署上线；缺效果评估报告与多用户隔离 |

## 七、效果评估（当前状态，如实说明）

| 指标 | 现状 | 下一步 |
|---|---|---|
| 路由准确率 | 未系统测量（人工验证 3 类意图） | 20 条标注用例 + 跑分脚本 |
| 工具调用正确率 | MCP 自检 63 项通过（协议层） | 任务级统计 |
| 引用命中率 | 工具层可返回文件名/章节/哈希，未统计 | 抽样统计引用正确比例 |
| 幻觉率 | 有"无依据拒绝"机制，未量化 | 构造 20 条越界问题统计拒答率 |
| 端到端时延 | 简单问答 2–5 秒；出题 30–60 秒 | 缓存/预生成 |

> 我们选择如实标注：**效果评估是当前最薄弱的一环**，也是校赛后最先补齐的部分。

## 八、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 平台侧凭据/实例状态变化（404/401/403） | 演示中断 | 每日开工先跑连通性自检；演示前一天冻结版本，不再重新部署 |
| 出题耗时 30–60 秒 | 现场等待 | 演示前预生成题目，现场只演作答与判分 |
| 工作流节点参数类型不匹配 | 工具调用失败 | 结构化参数改用 JSON 文本 + 服务端容错解析；schema 变更后重加节点 |
| 模型编造引用 | 可信度受损 | 引文由服务端截取；无依据直接拒答 |
| 多用户隔离未做 | 无法多人试用 | 演示期固定演示账号；后续接登录与 userId 隔离 |

## 九、附录

### 9.1 知识点数据模型

```text
courses            {userId}:{courseName}
knowledge_points   kpId（含 name / aliases / course / source）
profiles.mastery   kpId → masteryScore / assessed / attempts
```

规则：**知识点必须属于课程；任何"说法"先归一成 kpId；简称有歧义时不猜。**

### 9.2 关键接口（网关）

```text
POST /api/v2/agent/chat          主链路（SSE）
POST /api/v2/agent/grade         判分聚合（得分/逐题/掌握度/重排/平台点评）
GET  /api/v2/agent/catalog       课程与知识点目录
POST /api/v2/agent/schedule      课表导入（图片或文本）
POST /api/v2/agent/deadlines     作业/考试 DDL 导入（文本解析）
GET  /api/v2/agent/wrongbook     错题本
POST /api/v2/agent/vision        拍题识别
```

### 9.3 术语

| 术语 | 含义 |
|---|---|
| kpId | 知识点唯一标识（注册表主键） |
| assessed | 是否已通过判分获得真实掌握度 |
| sessionRef | 平台会话引用的业务映射，用于换取 userId |
| 降级 | 平台不可用时仍有可用输出，并显式标注 |
