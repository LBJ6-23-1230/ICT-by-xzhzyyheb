# S5 数据入口与图片诊断方案

> 现状：画像、计划、题目、讲义全部由**我们脚本种进服务器**。用户（评委/同学）无法自己上传资料，
> 也无法拍照诊断。演示时只能"我们准备好数据给他看"，说服力弱一半。
>
> 这两个缺口必须在 S5 补齐：**用户能上传、能拍照**，系统才叫"应用"。

## 一、缺口盘点

| 能力 | 原项目 | 现状 | 缺什么 |
|---|---|---|---|
| 用户上传讲义 | 有（`POST /api/v1/knowledge-bases/{kbId}/documents`） | 只有脚本种子 | Web 端上传入口 + 跨进程可见 |
| 拍照/上传错题 | 有（qwen-vl 识别 + 诊断） | **完全没有** | 图片入口 + 识别链路 |
| 用户注册/登录 | 有 | 未接（demo-user） | 可先不做，但要知道这是缺口 |
| 查看自己的数据 | 有 | 未接 | S5 前端展示 |

## 二、数据入口：三条路，选第 2 条

| 方案 | 做法 | 问题 |
|---|---|---|
| 1. 平台知识库上传 | 用户在 AgentArts 控制台上传 | 控制台是**开发者**界面，终端用户进不去；基础版每应用 1 个库 |
| **2. 网关上传（推荐）** | Web Demo 选文件 → 网关解析入库 → MCP 检索 | 需要网关与 MCP 共享数据 |
| 3. 脚本种子 | 我们现在这样 | 只能演示固定数据，不能自称"用户上传" |

### 为什么必须切 SQLite

```
网关进程（上传文档） ──写──► repository.json
                                  │
MCP 进程（检索资料） ──读──► 自己的内存缓存   ← 看不到新文件！
```

`JsonRepository` 启动时全量读入内存、之后不重读。所以**网关上传的资料，MCP 永远查不到**，除非每次上传后重启 MCP——演示时不可能这么做。

**解决：两个进程都切 SQLite**（`ZHIXUE_DB=sqlite`）。SQLite 每次查询都读盘，跨进程天然可见。

```bash
# 网关 .env 和 mcp.env 都加
ZHIXUE_DB=sqlite
```

迁移现有 JSON 数据：`python tools/migrate_repository.py`（仓库已有脚本）。

### 上传链路

```text
Web Demo「上传讲义」
   │ multipart：file + courseName
   ▼
网关 POST /api/v1/knowledge-bases/{kbId}/documents   ← 现有接口，无需新写
   │ 解析 pdf/docx → 切片 → 写 documents/chunks
   ▼
SQLite
   ▲
   └── MCP search_learning_materials / create_grounded_exercise 读取
```

**结论：后端不用改，只需要把网关跑起来 + 切 SQLite + 前端加一个上传按钮。**

## 三、图片错题诊断：两条路，先做 B

### A. 平台视觉输入（能力有，风险未知）

工作流的「大模型」节点有 **视觉理解输入** 配置项，理论上可把图片直接喂给平台模型。
但运行时 API 是否接受图片、图片怎么传（URL / base64 / OBS），文档没写清楚，**需要实测**。

### B. 网关侧识别（推荐，确定性强）

```text
Web Demo「拍照 / 选图」
   │ 图片 base64
   ▼
网关 POST /api/agent/chat（带 image）        ← 现有接口，已接 qwen-vl
   │ 识别：题目文本、知识点、错因
   ▼
文本化结果（题干 + 知识点 + 错误类型）
   │ 作为 query/inputs 传给 AgentArts 运行时
   ▼
wf-diagnosis / wf-assessment 继续流程
```

优点：

1. **复用已测过的识图链路**（`chat_llm._call_llm_with_image`），不依赖平台未验证的能力
2. 识别与诊断解耦：图片识别失败时，用户仍可手动输入题目文本
3. 换成其他视觉模型只改一处配置

缺点：图片不进入 AgentArts Trace（评委看不到"平台侧处理了图片"）。补法：网关把识别结果与图片哈希一起写进 `agentarts_runs`，Trace 面板并排展示。

## 四、改动清单

### 后端（网关）

| 文件 | 改动 |
|---|---|
| `.env` | `ZHIXUE_DB=sqlite`；`DATABASE_URL` 不需要（本地 sqlite 文件） |
| `app/api/agentarts_api.py` | 新增 `POST /api/v2/agent/upload`：接收文件 → 复用 knowledge 上传逻辑 → 返回 `documentId/kbId` |
| `app/api/agentarts_api.py` | `POST /api/v2/agent/vision`：接收 base64 → 调识图 → 返回结构化题目，供前端再提交诊断 |

> 上传与识图都可以直接复用现有实现，新增的只是"v2 命名空间下的薄封装"。

### 前端（Web Demo）

| 区域 | 交互 |
|---|---|
| 左侧输入框 | 加「📎 上传讲义」「📷 拍错题」两个按钮 |
| 上传后 | 显示"已解析：二叉树讲义.pdf，12 个切片"，并提示"现在可以问我这份资料里的内容" |
| 识图后 | 显示识别结果（题干 + 知识点），并预填到输入框，用户确认后再发 |

### 数据

| 项 | 动作 |
|---|---|
| 现有 JSON 数据 | `tools/migrate_repository.py` 迁到 SQLite |
| 演示账号 | 保留 `u-demo`，但上传/识别后数据要能**当场变化**（评委看到"我刚传的资料它就能用"） |

## 五、验收

| # | 操作 | 期望 |
|---|---|---|
| U1 | Web 端上传一份新讲义（如"图算法讲义.pdf"） | 返回 `documentId`，切片数 > 0 |
| U2 | 紧接着问"图算法里 Dijkstra 怎么讲" | 回答引用**新上传**的文件名与章节 |
| U3 | 不重启 MCP | U2 仍成立（证明 SQLite 生效） |
| V1 | 上传一张错题照片 | 识别出题干与知识点，预填到输入框 |
| V2 | 确认后发诊断 | 走 `wf-diagnosis`，结论基于识别出的知识点 |
| V3 | 传一张模糊/无关图 | 明确说"没识别出题目"，不硬编知识点 |

U3 和 V3 是"防假"的关键：一个证明数据真共享，一个证明识别失败不会编造。

## 六、演示话术（评审会问）

> "资料不是我们预先塞进去的。评委可以现场传一份讲义，系统解析后立刻能基于它出题；
> 拍一张错题照片，它先识别题目和知识点，再走诊断流程。
> 识别和诊断分工明确：识别失败会如实说，不会硬编一个知识点。"

这段话的前提就是上面 U1–U3、V1–V3 全部跑通。
