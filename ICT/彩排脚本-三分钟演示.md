# 三分钟演示彩排脚本

> 目标：不是"跑一遍看看"，而是**同时收集三类信息**——能不能跑、哪里会卡、哪里可以变成创新点。
> 每轮彩排填一张记录表，两轮后按判定标准决定"能不能拍视频"。

## 一、彩排前 5 分钟（照抄执行）

```bash
cd /opt/zhixue

# 1. 两个服务在跑
systemctl is-active zhixue-mcp zhixue-gateway

# 2. MCP 12 个工具
curl -sk https://<IP>:8443/healthz -H "X-API-Key: <MCP Key>"

# 3. 网关与云端配置
curl -s http://127.0.0.1:5000/api/v2/agent/runtime | head -c 200; echo

# 4. 依据链接口
curl -s http://127.0.0.1:5000/api/v2/agent/profile | head -c 200; echo
curl -s "http://127.0.0.1:5000/api/v2/agent/knowledge?q=后序遍历" | head -c 200; echo

# 5. 复位到演示基线
python3 tools/reset_demo_data.py

# 6. 冒烟：一句话能看到 wf-planner
curl -N -s --max-time 60 -X POST http://127.0.0.1:5000/api/v2/agent/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"我今晚只有60分钟怎么安排","sessionId":"chat-smoke"}' | tail -6
```

六条全过再开浏览器。任何一条不过，先修。

## 二、彩排分镜（R1：功能验证，允许调试）

| # | 时间 | 操作 | 输入 | 预期 | 失败预案 |
|---|---|---|---|---|---|
| 1 | 0:00 | 打开 `http://<IP>:5000/demo` | — | 顶栏 `云端 AgentArts` + 运行时名 | 显示"网关不可用"→ 查网关 |
| 2 | 0:20 | 问薄弱点 | 帮我看看我哪里薄弱 | 时间线出现 `wf-diagnosis`；回答列薄弱点 + 掌握度 | 进错工作流 → 查控制器路由 |
| 3 | 0:50 | 问时间安排 | 我今晚只有60分钟怎么安排 | 时间线 `wf-planner`；任务排满 + 延期带原因 | 报 `availableMinutes` → 查节点默认值 |
| 4 | 1:30 | 拍错题 | 一张清晰选择题 → 发送"我错了，帮我看看" | 识别出题干；回答讲解；掌握度下降 | 识别失败 → 换清晰图 |
| 5 | 2:10 | 再问薄弱点 | 帮我看看我哪里薄弱 | **刚才那个知识点位置变了** | 没变 → 错题没落库（查 wrong_book） |
| 6 | 2:40 | 上传讲义后出题 | 上传 .md → "根据这份资料出两道题" | 题目带"依据：文件名 · 章节" | 无资料 → 查切片匹配 |

## 三、每一步的"创新观察点"（彩排时重点看这些）

彩排的真正价值在这里：**看哪些瞬间"让人眼前一亮"**，那些就是要放进视频和答辩的。

| 步骤 | 观察什么 | 如果成立，它就是创新点 |
|---|---|---|
| 1 | 徽标是否来自接口而非写死 | "云端/降级"如实显示，可作为"可观测"卖点 |
| 2 | 时间线是否显示"进了哪个 Agent" | 多 Agent 协作可视化 |
| 3 | 延期是否**带原因**（不是默默丢掉） | "预算不足延期 25 分钟"比"排好了"有说服力 |
| 4 | 回答下方是否有 🧮 / 📚 入口 | **依据可点开**（目前最核心的创新） |
| 4 | 数字旁是否标了"计算/生成" | 模型与计算分离，交互可见 |
| 5 | 同一句话两次问，答案是否**不同** | 闭环可见：学情真的变了 |
| 6 | 无资料时是否**拒答**而不是编 | "没有依据就不编"比"能答"更可信 |

### 额外留意（彩排中可能自然出现，出现就记下来）

1. **控制器"排除项"**：如果时间线能看出"为什么没走别的 Agent"，这是最强的创新点候选人。
2. **失败路径**：任何一次报错，如果系统**如实说"失败"而不是假装成功**，这就是可展示的边界能力。
3. **等待态**：识别/排期时是否有"思考中"提示，而不是白屏 3 秒。
4. **数字一致性**：回答里说"掌握度 54"，点开依据是否也是 54——不一致就是必须修的 bug。

## 五、判定标准

| 灯 | 条件 | 下一步 |
|---|---|---|
| 🟢 绿 | 6 步全过，且第 4/5/6 步的预期现象都出现 | 直接拍视频 |
| 🟡 黄 | 4–5 步过，卡点在**平台侧**（模型鉴权/工作流参数） | 修 1 次再彩排，同时准备"备用模型"预案 |
| 🔴 红 | 第 3 或第 5 步不过（排期/闭环） | 停止彩排，先修主链路 |

**黄灯也要开录**：录一个"能跑的部分"，比等到全绿再录更实际。

## 六、R2：正式计时（不动手，只看时间）

R1 通过后，按脚本**不做任何调试**再走一遍，只记两件事：

1. 每一步实际耗时（目标：6 步在 3 分钟内）
2. 哪一步的等待 >5 秒（超过就要在视频里剪掉或加旁白）

## 七、常见故障与现场话术

| 现象 | 原因 | 话术（不要解释技术细节） |
|---|---|---|
| 工具全超时 | 平台 MCP 地址失效 | "云端工具连接异常，我切到已缓存的结果演示" |
| `100025` 模型鉴权 | 平台模型 Key 失效 | "云端模型鉴权过期，我换备用模型" |
| 回答是"请提供相关信息" | 控制器缺参数 | 重新说一句完整的话（带时间/知识点） |
| 判分 `NOT_FOUND` | 题号不存在 | "这道题不在题库里，我换一道" |
| 页面打不开 | 安全组/服务 | 提前准备本地截图备份 |

**原则：不要在现场排查问题。** 说一句"这步我先跳过，稍后展示"，继续往下走。
